# Restaurant Inventory SOP · 餐饮库存与配方管理

一个以餐饮门店实际录入、采购和盘点流程为出发点的本地优先进销存项目。目标是让库存数据可追溯、输入不丢失、单位换算清楚，并用菜品 SOP 与销量计算理论原料耗用，供实际出库核对。

**欢迎公开审查、提 Issue 和 Pull Request。当前是社区审查版，不是经过第三方认证的商用 ERP。**

## 项目介绍

门店常见痛点包括：入库反复选商品、规格和单位；包装与克重不统一；删除后表单失去响应；切换页面丢草稿；批量导入一个错误阻断全部工作；配方名与库存名不一致；采购、盘点和实际耗用难以相互核对。

本项目围绕这些问题实现统一库存流水、可搜索选择、总览快捷操作、草稿保留、导入预览与事务、单位换算、成本守恒和配方人工核实机制。

## 已有能力

- 商品建档：名称、SKU、分类、规格、采购/库存单位、包装关系、净含量和补货参数。
- 库存总览：分类筛选、关键词搜索、分页、平均成本、库存预警、快捷入出库和清理反馈。
- 库存作业：入库、出库、领退料、报损、调整；失败保留输入；稳定请求防重。
- 采购管理：供应商、采购草稿、分批收货、关联原单退货；退款与库存价值分开。
- 配方管理：原料搜索、相似名称候选、手动修正、重量换算、进料率和未保存草稿。
- 库存对账：明盘/盲盘草稿、打印 Excel、盘点导入、差额确认和草稿删除。
- 销量核对：销售 SKU / 菜名匹配、歧义人工确认、按仓库保存理论耗用。
- Excel / Word 导入：服务端校验、批次事务、重复提交保护、逐项错误说明。
- 本地 SQLite 存储、审计记录、闭账约束，以及 Windows Electron 桌面构建支持。

**配方保存不会自动扣库存。** 当前销量导入生成理论耗用供核对；实际库存仍以库存作业/业务单据为准。收银系统 API 实时接入未完成，不应据此宣称已与任何收银品牌打通。

## 技术栈

Next.js 16、React 19、TypeScript、SQLite（better-sqlite3 + Drizzle）、Electron、Vitest、Testing Library。安装版本以 `pnpm-lock.yaml` 为准。

## 本地启动

开发验证环境为 Windows + Node.js 26。切换 Node/Electron 版本后须重建原生 SQLite 模块。

```powershell
pnpm install --frozen-lockfile
pnpm native:rebuild:node
pnpm dev
```

打开 `http://127.0.0.1:3000`。首次访问创建本地数据库，只加载虚构示例商品，不含营业额、供应商或历史库存。若需要空白模式，启动前设置 `$env:RESTAURANT_SEED_MODE="blank"`。

默认数据库在运行目录的 `data/`；可用 `RESTAURANT_DATA_DIR` 指定独立位置。不要用真实门店数据库做审查或测试。

```powershell
pnpm typecheck
pnpm test
pnpm build
```

`pnpm test` 自动指定 `.review-temp/` 下独立账本。Windows 桌面构建命令是 `pnpm desktop:build`；首次执行需下载 Electron/打包依赖。公开桌面版使用单独应用 ID 和用户数据目录，不接管原门店版账本。

## 重点邀请审查

1. 数量与成本守恒：克级单价、混价采购、分次出库、退款与库存价值的区别。
2. 写入边界：批量失败回滚、重复请求、跨门店/仓库关联、历史入库删改和闭账。
3. 配方匹配：多候选、计数包装不明、重量/体积不混换、进料率和失效原料引用。
4. 交互恢复：删除后继续输入、切页/重挂载保留草稿、旧响应不覆盖新输入。
5. 恢复与发布：WAL 一致快照、升级备份、启动失败反馈和原生模块兼容。
6. 性能：大量流水、配方和低配 Windows 下的查询与交互延迟。

请在 Issue 中写清复现步骤、预期与实际结果、系统/Node 版本及脱敏日志。贡献方法见 [CONTRIBUTING.md](CONTRIBUTING.md)，安全漏洞见 [SECURITY.md](SECURITY.md)。

## 公开范围与限制

本仓库不包含真实餐厅的经营报表、数据库、供应商资料、内部 SOP、产品成本卡、PDF/Word 原稿、个人本机路径或已打包门店安装程序。示例名称和数量均为虚构，不能作为食品加工标准。

本地原版的回归与发布验收不能自动视为本公开版通过；公开版的实际验证结果记录在 [docs/REVIEW_STATUS.md](docs/REVIEW_STATUS.md)。

目前不适合将本地服务直接暴露到公网：有单机默认门店上下文和早期认证/财务接口，尚未完成全面多用户授权审查、恶意文件防护、真实输入法及跨电脑故障验收。对这些缺口的独立审查非常欢迎。
